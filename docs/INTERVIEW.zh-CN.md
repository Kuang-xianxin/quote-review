# 面试讲解：从字段提取到可核对的采购流程

## 一分钟说明

“这个项目解决供应商报价格式不统一的问题。用户上传文件，本地开源模型提出结构化字段，人对照原文确认后才能比价。它的工程重点是避免单位和币种混用，并让任务中断、人工修改、并发保存有明确的数据状态。模型没有直接决定采购。”

只在理解并实际复现后用自己的话讲述。开发使用了 AI 协助；不要声称全部独立手写、存在真实客户或已节省某个百分比时间。

## 可以现场演示的链路

1. 上传中英文样例，看到真实后台任务；比较整箱报价与单件报价。
2. 指出引用原文、模型遗漏与人工修正，解释为何勾选确认后才参与比较。
3. 修改包装件数，重新确认，观察每件价格变化，但不把它叫含税到岸成本。
4. 刷新页面仍有资料；两个页面同时编辑旧版本，说明 409 冲突和审计记录。
5. 取消一个执行任务，再解释过期租约如何拒绝旧计算节点的结果。

## 技术追问

**为什么不直接问大模型哪家便宜？** 它可能混淆箱和件，猜币种或忽略起订量。模型负责提取建议；确定性代码负责数据约束、十进制换算，人工负责规格等价和决策。

**结构化 JSON 是否等于正确？** 不等于。基线模型在合法 JSON 中填过错误单位、猜测币种、漏表格行，还受到文档里的恶意文字影响。回归数据保存了这些失败，不能只展示通过样例。

**怎样防重复执行？** 领取任务用单条原子条件更新；每次租约生成新令牌。结果写回检查令牌、有效期和状态。幂等完成不增加第二份结果；取消使令牌失效。

**为什么数据库事务还不够？** 文件存储与数据库不在同一事务里。上传后数据库失败要清理文件；删除先处理文件，失败时留记录供重试。该实现仍需生产级监控、补偿队列和备份策略。

**如何衡量价值？** 下一步找愿意提供脱敏报价的采购人员，以人工结果为参考，记录各字段错误、遗漏行数、修正耗时与完成比价所用时间。没有真实用户数据前，不声称“效率提高 XX%”。

**如何扩展？** 优先按实际错误补扫描 OCR、表格行对齐和更完整评估；在真实协作需求出现后再加账号权限。当前计算节点靠一台电脑，不声称高可用或大规模生产能力。
